# Приложение диспетчера

Приложение состоит из интерфейса на Next.js и предметных проверок на Rust. Это одна приватная локальная рабочая среда для владельца очереди. Она помогает назначать короткие консультации и сохранять результат. Подключения к аккаунтам, событиям и уведомлениям Stavleak здесь нет.

## Рабочий путь

1. Запустите приложение по инструкции корневого README и войдите как владелец. Начальные данные пустые.
2. Добавьте ментора: внутренний код, имя или рабочую роль, темы, языки `ru`, `kk`, `en`, начало и конец подтверждённой доступности. Пока подтверждение выключено, рекомендации не используют этого человека.
3. Примите вопрос команды: уникальный номер, внутренний код команды, одну тему, язык, безопасный контекст, момент готовности, владельца, срок обновления и следующее действие. У команды может быть один открытый запрос.
4. Обновите очередь и рекомендации. Назначьте предложенного свободного ментора или выберите другого подходящего свободного специалиста с объяснением ручного исключения.
5. Свяжитесь с ментором и командой вне приложения. После фактического начала нажмите «Начать консультацию». При отмене до начала верните запрос в очередь: прежнее время готовности сохраняется.
6. В конце запишите согласованный итог и действие команды, выберите «Ответ получен» или «Согласовано самостоятельное действие» и завершите сессию. Новый вопрос после проверки получает новый номер и место в очереди.

Приложение не отправляет сообщения участникам. Срок означает следующее действие владельца; просроченный запрос остаётся видимым, а не закрывается автоматически. Время вводится и отображается в часовом поясе браузера, затем передаётся в Rust как RFC 3339 с явным смещением / UTC.

## Как считается назначение

Rust сортирует готовые запросы по реальному моменту `queued_at`, затем по номеру. Для каждого выбирает подходящего по теме и языку, подтверждённого и свободного ментора. В доступный интервал должен помещаться весь слот. Среди нескольких кандидатов используется меньшее число начатых сессий в этой рабочей среде, затем код ментора. Это узкое правило баланса нагрузки; оно не учитывает компетенции сверх отмеченных тем.

`assigned` уже резервирует ментора, `in_session` продолжает резерв. Одновременно два активных назначения одного ментора недопустимы. Если более ранний подходящий запрос пропущен, сервер требует `manual_exception`. Причина не позволяет назначить человека без нужной темы, языка или доступного интервала. Исключения остаются в записи и видны диспетчеру.

Рекомендация должна быть выполнима сама по себе: следующая команда с той же компетенцией получает предложение после сохранения назначения предыдущей. Приложение не считает ещё не сохранённое планируемое назначение состоявшимся. Каждое сохранение пересчитывает рекомендации.

Если подходящего подтверждённого покрытия нет, интерфейс показывает отсутствие специалиста. Если покрытие есть, но слот занят или ещё не начался, показывает ожидание. Владельцу нужно проверить резерв и сообщить команде доступный вариант. Закрытие без консультации требует явного подтверждения, что команда получила и согласовала такой исход.

## Сохранение и две вкладки

Каждое изменение отправляет полное новое состояние через общий `useWorkbench` вместе с версией. При конфликте версий интерфейс показывает сообщение и блокирует дальнейшие записи до загрузки актуального состояния. После загрузки сверяйте поля своей формы с изменившейся очередью и применяйте решение заново. Приложение не объединяет параллельные решения автоматически.

Постоянное хранение, HTTP-вход, аутентификация и проверка версий принадлежат серверному scaffold. Предметный модуль проверяет каждый сохраняемый JSON: типы и неизвестные поля, длины, количество записей, уникальные номера и коды открытых команд, ссылки на менторов, состояния, порядок времени, совместимость и отсутствие двойной сессии. Проверки браузера помогают заполнить форму; принять недопустимое состояние должен запретить Rust.

Дополнительно `validate_update` сверяет прежнее и новое состояния внутри серверной блокировки: запросы нельзя удалить, исходное время очереди и код команды не меняются, завершённые записи остаются неизменными, пропуск этапа назначения запрещён. Факты начавшейся сессии сохраняются. Назначение, начало и конец новой операции должны отражать настоящее время с допуском две минуты для часов устройства. Если время устройства расходится сильнее, исправьте его; существующие учебные исходники не позволяют переписывать историю.

## Учебные данные

Кнопка «Добавить учебный пример» запрашивает подтверждение и добавляет два вымышленных ментора и три запроса с префиксом `DEMO`. Их время сдвигается к моменту загрузки, чтобы можно было проверить рекомендацию, ожидание второй команды и отсутствие `hardware/kk`. Существующие записи сохраняются. Повторная загрузка этих же номеров отключена. Функция `default_data()` всегда возвращает пустые списки.

Учебные люди и вопросы не являются клиентскими результатами. Загружайте демо в отдельную учебную рабочую среду: закрытые учебные записи сохраняются так же, как обычные.

## Границы текущей версии

- Один владелец и одна рабочая среда; отдельных кабинетов команды, ментора и организатора нет.
- У ментора один интервал доступности; несколько смен описываются организационно, а действующий интервал меняется после завершения назначенных сессий.
- Темы вводятся внутренними кодами, например `tech`, `product`, `pitch`; автоматической классификации вопроса нет.
- Есть `queued`, `assigned`, `in_session`, `closed`, `cancelled`. Расширенный процесс из бумажного регламента с `needs_info`, подтверждаемой передачей смены и отдельным журналом решений остаётся организационным процессом. Интерфейс не выдаёт смену владельца за подтверждение другого человека.
- Состояние содержит текущие записи, времена и ручные причины. Полной неизменяемой истории всех правок и автоматической выгрузки метрик здесь нет; утверждённые исходы и исключения можно сверять в закрытой рабочей копии.
- Рекомендации пересчитываются при загрузке и сохранении. Текущее время может сделать рекомендацию устаревшей; перед назначением обновите очередь. Rust повторно проверит интервал фактического назначения.
- Приложение не решает конфликты интересов, инциденты безопасности, правила помощи и жалобы. Их принимает руководитель события приватно.
- Рабочие вопросы и контакты не предназначены для публичного GitHub. Не помещайте реальные данные в demoData, Issues или снимки экрана.

Лимиты этой версии: 100 менторов, 2000 запросов, слот 5–60 минут. Эти ограничения ограничивают размер локальной среды и не являются обещанием пропускной способности хакатона.

## Проверка предметной части

Rust unit tests в `backend/src/domain.rs` проверяют пустой старт и строгую структуру, дубликаты и ссылки, явную причину обхода очереди, несовместимую тему, двойное назначение, порядок с разными смещениями, нехватку полного слота, жизненный цикл и отсутствие следующего действия. Запуск: `cargo test --manifest-path backend/Cargo.toml --locked` из корня этого комплекта после сборки зависимостей.

Перед событием выполните учебный путь в интерфейсе: добавление и редактирование ментора, приём двух подходящих вопросов, назначение раннего, отказ двойного назначения, завершение и освобождение слота, отсутствие компетенции и конфликт двух вкладок. Успешные unit tests не заменяют этот прогон.
